# Event schema

**Context:** [README.md](README.md), [architecture.md](../architecture.md), [ws-contract.md](ws-contract.md).

An event is the unit of record in the session log. Everything that happened in a session can be fully reconstructed from events: AI dialogue, file changes, command runs. The event log is the single source of truth for the dashboard, replay, sharing, and any future features like analytics.

---

## Principles

1. **Append-only.** Events are not edited or deleted. A typo in a recorded event is a new event, not a correction of the old one.
2. **The backend is the emitter.** Events about candidate actions are produced server-side by the `AgentHost` (the agent loop that drives the browser candidate's sandbox) and by backend service logic (`session_end(timeout)`, `model_switched`). The invariant "event log = the complete truth about the session" holds.
3. **`seq` is assigned by the backend.** The backend assigns the next number from a monotonic sequence within the session when writing the event to the DB. This eliminates the class of errors "two clients argued about order" and simplifies reconnect/replay (see [ws-contract.md](ws-contract.md)).
4. **Deduplication by `id`.** Each event gets an `id: uuid v4` on creation; the writer (`store_event`) discards a duplicate by `id`. `id` lives for the whole lifetime of the event; `seq` appears after writing.
5. **Additions are additive.** A new event type or new field in `payload` is a non-breaking change. Deletion or semantic redefinition is breaking and requires a `protocol_version` bump (see [session.md](session.md)).

---

## Envelope

Each event is a JSON object:

```json
{
  "id": "8b1c4e3a-...",
  "seq": 142,
  "session_code": "K7M2-P9Q4",
  "timestamp": "2026-05-14T18:23:45.812Z",
  "type": "tool_call",
  "payload": { ... }
}
```

| Field | Type | Source | When appears |
|-------|------|--------|--------------|
| `id` | uuid v4 string | backend | on emission |
| `seq` | int (> 0, monotonic within session) | backend | on write to DB |
| `session_code` | string `XXXX-XXXX` | backend | on emission |
| `timestamp` | ISO 8601, UTC, milliseconds | backend | on emission (when the event actually happened) |
| `type` | enum (see below) | backend | on emission |
| `payload` | object (depends on `type`) | backend | on emission |

---

## Emitters within the backend

All events are emitted server-side by the `AgentHost` (the agent loop driving the candidate's browser session) plus backend service logic. The emitting subsystems by `type`:

| Subsystem | What it emits |
|-----------|--------------|
| **Candidate input** | `user_message`, `inline_bash` requests |
| **Agent loop** | `assistant_message`, `tool_call`, `tool_result` |
| **Sandbox FS** | `file_changed` (`source: agent` for Edit/Write tools, `source: manual` for the candidate's own editor saves, `source: baseline` for the scaffold) |
| **Sandbox shell** | `command_run`, `command_output`, `command_finished` |
| **Session lifecycle** | `session_start`, `session_end`, `assessment_pending`, `model_switched`, `sandbox_reset`, `sandbox_restored` |

The contract doesn't prohibit a different internal arrangement; the dashboard and backend rely only on the `type` values.

**What is NOT emitted:**
- Heartbeat — this is a WS frame, not an event. See [ws-contract.md](ws-contract.md).
- Low-level `llm_request`/`llm_response`. The full dialogue history is reconstructed from `user_message` + `assistant_message` + `tool_call` + `tool_result`. If needed for debugging, it can be added later as an additive type without breaking the dashboard.

## Event type catalog

### AI dialogue

#### `user_message`
Candidate sent a prompt.
```json
{ "text": "Extend train.py to support checkpoint/resume." }
```

#### `assistant_message`
Text response from the AI. Emitted once per completed model response (after all tool iterations of the corresponding reply).
```json
{
  "text": "I'll add a checkpoint now. Plan: ...",
  "usage": { "input_tokens": 4521, "output_tokens": 318 }
}
```
`usage` is optional (some providers don't return it; useful for weakness calibration).

**Streaming.** `assistant_message` is emitted as a single event on generation completion, without partial deltas. If the dashboard wants a "typing response", `assistant_message_delta` events can be added as an additive type.

#### `tool_call`
Agent called a tool.
```json
{
  "tool_call_id": "tc_8f3e...",
  "tool_name": "Edit",
  "input": { "file_path": "train.py", "old_string": "...", "new_string": "..." }
}
```
`tool_call_id` is a uuid v4 generated by the agent loop, links to `tool_result`. Tool names are canonical from [toolset.md](toolset.md).

#### `tool_result`
Result of a tool call.
```json
{
  "tool_call_id": "tc_8f3e...",
  "output": "Edit applied to train.py",
  "is_error": false
}
```
`output` is a string (including stderr and tracebacks when `is_error: true`).

**Optional tool-specific fields.** `payload` is free; specific tools can add optional fields on top of the required ones. Current contract:

- `Edit` / `Write`: `diff` — string, unified diff `old → new` (`a/<name>` → `b/<name>`). Empty/absent on a no-op or error. Rendered in the dashboard as a highlighted diff. For binary files, a placeholder `Binary file <name> changed`.
- `Bash`: `stdout`/`stderr` — strings (UTF-8, pre-capped at 1 MB per stream). Empty streams are omitted. `exit_code: int`, `duration_ms: int`, `timed_out: bool` (omitted if false) — the same values as in the `output` summary, but in separate fields for convenient rendering. The AI also gets the formatted stdout/stderr through the LLM history, independent of the event.
- `Bash` `tool_call`: `permission_decision` — string (`auto_allow` | `user_allow` | `user_deny` | `policy_deny`), `prompted` — bool. Reflects the permission gate decision:
  - `auto_allow` — gate verdict `allow` (whitelist), or the command prefix is session-allowed, or permission checks are skipped.
  - `user_allow` — verdict `confirm`, candidate approved.
  - `user_deny` — verdict `confirm`, candidate denied.
  - `policy_deny` — verdict `deny` (deny-list, no prompt shown).

  `prompted: true` means the candidate was shown a confirm prompt (i.e. decision ∈ {`user_allow`, `user_deny`}). Omitted when false (same convention as `timed_out`). For `user_deny`/`policy_deny` the accompanying `tool_result` has `is_error: true` with a descriptive message — the AI gets feedback and can try a different approach.

### Diffs (interactive apply)

Cycle: `diff_proposed` → `diff_accepted` or `diff_rejected`. Linked by `proposal_id`.

**When applicable:** only when the agent proposes edits for interactive approval. In auto-apply mode a `tool_call(Edit|Write)` goes directly to `file_changed(source: agent)` without the proposal cycle. The dashboard must correctly display both scenarios.

#### `diff_proposed`
Agent proposed a change, waiting for the candidate's decision.
```json
{
  "proposal_id": "pr_3a91...",
  "file_path": "train.py",
  "diff": "@@ -10,3 +10,8 @@\n ...unified diff..."
}
```

#### `diff_accepted`
Candidate accepted the proposal. After this event the agent applies the edit → the file watcher emits `file_changed(source: agent)`.
```json
{ "proposal_id": "pr_3a91..." }
```

#### `diff_rejected`
Candidate rejected the proposal.
```json
{ "proposal_id": "pr_3a91...", "reason": "I want a different approach" }
```
`reason` is optional (free text).

### Files

#### `file_changed`
A file or directory in the working directory changed. Emitted by the backend (sandbox mode).
```json
{
  "file_path": "train.py",
  "diff": "@@ -10,3 +10,8 @@\n ...",
  "source": "agent",
  "content": "import torch\n...",
  "op": "modified"
}
```
`source`:
- `agent` — the change was applied by the agent via the `Edit`/`Write` tool.
- `manual` — the candidate edited the file with their editor, or a bash command changed the filesystem (explicit and allowed behavior, see [architecture.md](../architecture.md)).
- `baseline` — the initial state of the file at session start. Emitted by `AgentHost._emit_task_baseline()` for each text file in the task bundle, once on fresh-session start, right after `session_start`. `diff` is empty/`null`, `content` contains the full content (binary files omitted). Not considered a "change" — the dashboard hides baseline entries in file history and uses them as the `before` content for the first real edit's diff (so a one-char edit shows a one-line diff, not the whole file).

**Optional field `op`** (additive). Describes what kind of filesystem change occurred:
- `modified` — file was created or its content was written/changed. Default when the field is absent (backward-compat).
- `deleted` — file or directory was removed. `content` is `null`.
- `created` — a directory was created (with `is_dir: true`), or a `baseline` file's initial state at session start (`source: baseline`, regular file).

**Optional field `is_dir`** (additive). `true` when the event refers to a directory rather than a file. Absent/`false` for regular file events. Emitted from the sandbox Docker backend for `mkdir`/`rmdir` operations detected via bash execution.

`diff` — unified diff against the previous state of the file known to the watcher. On create/delete events, a diff against an empty file or a full deletion.

**Optional field `content`** (additive). Full file content after the change:
- `string` — UTF-8 content (for text files);
- `null` — file deleted, or a directory event;
- field omitted — binary file (UnicodeDecodeError).

Used by the dashboard to render the current file state in the Files tab without reconstruction via apply-patch.

### Commands

Cycle: `command_run` → many `command_output` → `command_finished`. Linked by `command_id`.

#### `command_run`
```json
{
  "command_id": "cmd_5b22...",
  "command": "pytest tests/test_train.py -k checkpoint",
  "cwd": ".",
  "cols": 120,
  "rows": 30
}
```

**Optional fields `cols` and `rows`** (additive). Terminal dimensions on the candidate's side at command launch time. The dashboard reproduces these dimensions in xterm.js so that line wrapping matches what the candidate saw. Omitted if the size couldn't be determined (non-TTY) — the dashboard uses a fallback 120×30 in that case.

#### `command_output`
Chunk of stdout or stderr. Emitted as it arrives.
```json
{
  "command_id": "cmd_5b22...",
  "stream": "stdout",
  "data": "===== test session starts =====\n..."
}
```
`stream`: `stdout` or `stderr`.

**Stream labeling depends on the execution backend.** The Docker sandbox merges stdout+stderr into one stream, so every chunk is `stream='stdout'` and ANSI codes (colors, progress bars, `\r`-overwrite) pass through unmodified. The **local** sandbox (dev path) reads stdout and stderr as separate pipes, so its stderr chunks carry `stream='stderr'`. The dashboard renders `data` through xterm.js identically to the candidate's terminal regardless of the label.

#### `command_finished`
```json
{
  "command_id": "cmd_5b22...",
  "exit_code": 0,
  "duration_ms": 8412
}
```

### Session lifecycle

#### `session_start`
First event in the session. The backend emits it on `AgentHost` start (the first `/candidate-web` connect).
```json
{
  "task_id": "task-01-training-loop",
  "ai_config": {
    "model": "deepseek-v4-flash"
  },
  "protocol_version": 7,
  "cli_version": "web"
}
```
`ai_config` is a snapshot of what the backend gave the client (see [session.md](session.md)). The duplication is needed: during replay the dashboard sees the session config directly in the event log, without depending on separate tables.

#### `session_end`
Last event. Emitted by the backend on normal completion or when the session was ended by the interviewer/timeout.
```json
{
  "reason": "interviewer | timeout | candidate_quit | error | submitted",
  "details": "optional string"
}
```
`submitted` — the candidate ended an async session early via the `session_submit` WS frame. `timeout` (async) — the server-side countdown hit the deadline (`started_at + time_limit_seconds`); see [session.md](session.md).

### Service events from the backend

#### `model_switched`
The backend switched to the next model in `ai_config` (graceful degradation on 5xx/provider timeout, see [architecture.md](../architecture.md), "Graceful degradation"). The candidate and interviewer see a notification — this is not a hidden degradation.
```json
{
  "from_model": "deepseek-v4-flash",
  "to_model": "anthropic-haiku-4-5",
  "reason": "provider_5xx | provider_timeout | quota_exhausted"
}
```

#### `session_end` (backend-initiated)
Same type as in lifecycle, but emitted by the backend with `reason: interviewer` or `reason: timeout`.

#### `sandbox_reset`
Emitted by the backend when the candidate's sandbox is reset to the task baseline. The container is destroyed and recreated with the task baseline; the conversation history is preserved, only the FS is reset. Two triggers:
- **Interviewer reset** via `POST /sessions/{code}/sandbox/reset` — the payload is empty (`{}`).
- **Auto-reset after expiry** — on the candidate's first reconnect to an expired sandbox the backend reprovisions a fresh one and emits `{"reason": "expired"}`.

```json
{ "reason": "expired" }
```
`reason` is **optional**: `"expired"` for the post-expiry auto-reset, **absent** for an interviewer-triggered manual reset (the candidate UI maps an absent `reason` to a "manual reset" notice). The event itself is the signal — the candidate UI clears the file tree and shows a notice; the interviewer dashboard renders a divider in the transcript and re-fetches the file tree.

**Invariant note:** `sandbox_reset` is a backend-emitted service event; the correlational invariants (§Invariants 3–5) do not apply to it.

#### `sandbox_restored` (web runtime only)
Emitted by the backend after a fresh sandbox has been provisioned for an existing session and the event-log file-state projection has been replayed onto it. Surfaced to the dashboard and candidate UI as a "Sandbox restored from history" notice. Only emitted when at least one file was written or deleted during replay; fresh sessions (an empty projection) do not produce this event.
```json
{
  "file_count": 12,
  "deleted_count": 2
}
```
`file_count` — number of paths written via `provider.write_file`. `deleted_count` — number of paths removed via `rm -rf`. Both are best-effort: per-path failures are logged and skipped, so the counts reflect successful operations only.

**Invariant note:** `sandbox_restored` is a backend-emitted service event; the correlational invariants (§Invariants 3–5) do not apply to it. It can only appear in sessions that already have a `session_start` event (i.e. on resume).

#### `assessment_pending` (async sessions only)
Emitted by the backend on the `active → completed` transition of an `async` session (both terminal paths — candidate `session_submit` and server-side `timeout`). It is the hook for the AI assessment job.
```json
{ "reason": "submitted | timeout" }
```
`reason` mirrors the accompanying `session_end.reason`. Emitted **immediately before** the terminal `session_end` (the event log closes on `session_end` — invariant 2 — so a post-end event would be rejected). Exactly one `assessment_pending` per session: the terminal transition is serialised server-side, so a submit racing the timeout cannot double-emit it.

**Invariant note:** `assessment_pending` is a backend-emitted service event; the correlational invariants (§Invariants 3–5) do not apply to it. It can only appear in sessions that already have a `session_start` event.

## Correlation IDs

| ID | Generated by | Links |
|----|-------------|-------|
| `tool_call_id` | agent loop | `tool_call` ↔ `tool_result` |
| `proposal_id` | agent loop | `diff_proposed` ↔ `diff_accepted`/`diff_rejected` |
| `command_id` | backend shell wrapper | `command_run` ↔ `command_output` ↔ `command_finished` |

All three are uuid v4. They don't overlap by namespace.

---

## Invariants

The backend checks on write; a violation returns an error to the client and the event is not written:

1. **`session_start` is the first event of the session.** Any event before it is rejected.
2. **No events after `session_end`.** The backend closes writing.
3. **`tool_result` references an existing `tool_call_id` in the same session.** Otherwise, an error.
4. **`diff_accepted`/`diff_rejected` references an existing `proposal_id`.** Each `proposal_id` is closed by exactly one event.
5. **`command_output`/`command_finished` references an existing `command_id`.** Each `command_id` is closed by exactly one `command_finished`.
6. **`id` is unique within the session.** A repeat is deduplicated, not an error.

Invariants 1 and 2 are hard session boundaries. The rest are correlational; their violation almost always means a bug in the emitter.

---

## Deferred / not implemented

- `llm_request`/`llm_response` as separate events — deferred, see the Principles note.
- `assistant_message_delta` for streaming — deferred.
- Events for multi-cursor / collaborative editing — not in the product.
- Events for interviewer scoring — not in the platform (assessment is external to the session).
- Event signatures (HMAC) for tamper protection — trusted in the current model.
